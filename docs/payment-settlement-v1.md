# Task 7 payment and settlement contract

This contract adopts the Customer proposal's full-balance payment, visit scope, integer KES minor units, version checks, immutable receipts, and final settlement rules. The wire schema for adapter integration is [payment-settlement-v1.openapi.json](payment-settlement-v1.openapi.json). Cash is the first live method. Manager-confirmed collection uses the existing protected cookie and CSRF session. Kitchen and terminal credentials cannot attest receipt of cash.

The terminal reads the payable balance, explicitly reviews the returned `billVersion`, and posts its method with a UUID `Idempotency-Key`. The server determines the amount and locks the visit during any attempt that can still settle. Identical replay returns the same attempt even after settlement. Changed replay returns `IDEMPOTENCY_CONFLICT`. Refresh and obtain new confirmation on `BILL_VERSION_CONFLICT`. Do not create a new attempt while `PAYMENT_PENDING` applies. The first slice supports one successful full-balance settlement per visit, with no tips, split tender, refunds, or further rounds after settlement.

A cash attempt starts `PENDING`. The Manager confirms only after collecting the amount due and returning any change. The Manager sends `expectedVersion` and `expectedBillVersion`. Double confirmation with the same confirmed versions returns the existing success and receipt. A terminal cancellation records intent and remains `PENDING` until the Manager verifies that no cash was taken. The Manager can then record `CANCELLED`, or `FAILED` when a cash collection did not succeed, with a reason. The customer projection omits the internal audit and cashier identity.

An unresolved Chef decision blocks payment initiation and final closure. New rounds and payable changes require the visit payment lock. Preparation and explicit handoff can continue because they do not change the payable amount. Visit closure requires no pending payment, no outstanding balance, and physical handoff of every payable order. Staff can close a visit after expiry if these checks pass. Reviews continue to depend on actual handoff. Customer can retrieve an existing payment or receipt using the original terminal after closure or expiry.

## Provider preparations

- **M-Pesa Daraja sandbox** requires a Safaricom sandbox app enabled for M-Pesa Express, OAuth consumer key and secret, the sandbox business shortcode and STK passkey, enabled transaction type, sandbox test MSISDN, and a public HTTPS callback URL. Persist the checkout request and merchant request IDs. Keep attempts pending on timeout, reconcile against the provider query, and require confirmed merchant, transaction identity, and exact amount before issuing a receipt. The merchant's product specification and sandbox must confirm the accepted amount representation and limits before activation. Until then, reject fractional-shilling balances for this method and never round the authoritative KES balance. [Safaricom Daraja](https://developer.safaricom.co.ke/)
- **Hosted card candidate** requires merchant approval and an account enabled for KES card presentment. Stripe Checkout would use the backend test secret, hosted return and cancel URLs, an HTTPS webhook endpoint with its separate signing secret, and its account-specific test card configuration. Verify the raw webhook signature, deduplicate event and payment identities, and independently retrieve settlement state to confirm the provider account, currency and exact amount. KES uses two decimals, so KSh 325.50 is sent as `32550` to Stripe if this provider is approved. Verify merchant-country onboarding, settlement currency and account limits separately. [Hosted Checkout](https://docs.stripe.com/payments/checkout) · [Currency units](https://docs.stripe.com/currencies) · [Webhook verification](https://docs.stripe.com/events/manage-webhook-endpoints)

Deploy only approved callback routes through public HTTPS ingress. Keep the staff, Customer and database endpoints private. Use separate sandbox and live secrets and reconciliation records. Until the relevant provider is enabled, `MPESA` and `CARD` return `PAYMENT_METHOD_UNAVAILABLE` before an attempt is created. A redirect, customer statement, timeout, or unverified callback never constitutes payment success.

For deployment configuration, reserve `ROSE_DARAJA_CONSUMER_KEY`, `ROSE_DARAJA_CONSUMER_SECRET`, `ROSE_DARAJA_BUSINESS_SHORTCODE`, `ROSE_DARAJA_STK_PASSKEY`, `ROSE_DARAJA_TRANSACTION_TYPE` and `ROSE_DARAJA_CALLBACK_URL` for the approved Daraja adapter. Use the test MSISDN in controlled sandbox runs. If Stripe is selected, reserve `ROSE_STRIPE_SECRET_KEY`, `ROSE_STRIPE_WEBHOOK_SECRET`, `ROSE_STRIPE_SUCCESS_URL` and `ROSE_STRIPE_CANCEL_URL`. These settings describe the provider handoff and take effect only when an approved adapter is deployed. The cash slice requires none of them.

Reserve `/api/v1/providers/daraja/mpesa-express/callback` and `/api/v1/providers/stripe/webhook` for the approved deployment. Register the exact externally reachable HTTPS URL with each provider. Keep Checkout success and cancel redirects separate from the webhook URL. Reconcile the received event with the relevant provider status API before updating the payment ledger. The provider routes are planned and are absent from the cash deployment.
