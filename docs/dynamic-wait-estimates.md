# Dynamic order-ready estimates

Use the existing `POST /api/v1/wait-estimates` operation and `WaitRequest` and `WaitEstimate` schemas. The terminal bearer must own the active session. Derive the restaurant, table, catalog, preparation requirements, and priorities on the server. Use the same catalog and allergen validation as quotation. Estimation makes no reservation and has no effect on accepted prices, preparation holds, or status. The range measures time until food is ready for handoff.

Flyway V13 adds persisted station and prep-profile inputs. Manager station, prep-time, and Chef availability changes use the existing Admin cookie and CSRF token. Managers configure parallel slots and qualified Chef assignments separately from each person's expiring availability. The server derives the available Chef count. Existing lines with no station snapshot remain unassigned. Accepted lines with a profile retain their station and planned duration, and the server records their actual preparation start.

Read one consistent database snapshot of active stations, their configured parallel capacity, the on-duty and enabled staff assigned to them with the required qualifications, current item preparation state, and catalog preparation profiles. Each chef contributes at most one concurrent slot across stations. Cap slots by station capacity. Snapshot station and planned duration on acceptance so later catalog edits apply to new work. Apply configured quantity and option workload only when there is an explicit profile. Use start timestamps and elapsed work for PREPARING items while retaining a calibrated upper bound for overruns.

Simulate work already in preparation first. Schedule queued eligible work by audited priority, then acceptance sequence. Rush changes queue position without interrupting preparation. A Delayed marker communicates an operational issue and changes the estimate only when its underlying delay is reflected in capacity or workload. Use qualification-aware slot assignment, including chefs who cover multiple stations. Include the current draft after committed work in the applicable priority class. The ready time is the last draft line to finish across stations. READY and handed-off lines consume no preparation slots. Held and declined lines cannot be scheduled. A draft requiring Chef review returns `ALLERGY_REVIEW` because the start time is unknown.

Return `MISSING_PREP_PROFILE` when a required profile is missing, `NO_CAPACITY` when any required station has no effective capacity, and `STALE_WORKLOAD` when inputs cannot be read consistently, availability has expired, or a reliable range within the schema limits cannot be computed. Use a measured preparation range, round outward to whole minutes, and enforce `minimumMinutes <= maximumMinutes`. Set `calculatedAt` from the server clock and `validUntil` to the earliest input expiry, capped at 30 seconds. Refresh expired estimates and invalidate cached results on committed changes to queue state, permissions, assignment, availability, or capacity. The client should show the unavailable state when it cannot refresh.

Before exposing the estimate, verify overlapping assignments, a full station, an off-duty or disabled chef, a missing profile, stale input, multiple parallel stations, quantity changes, Rush precedence, held lines, and excluded READY lines against PostgreSQL. Verify that one terminal cannot obtain an estimate using another terminal's session. Keep these semantics within the existing wire shape and coordinate any schema changes with Customer.

## REST adapter handoff

`POST /api/v1/wait-estimates` takes the existing session ID and draft lines, including the actual line allergy declarations and selections. Send the optional `visitAllergy` when available, using the same value as quotation. The server never trusts a client-supplied preparation duration, projected capacity, or approval flag.

`GET /api/v1/orders/{id}/wait-estimate` is an additive terminal-owned read. It uses the same `WaitEstimate` response schema without changing the order or history envelope. Refresh relevant estimates at expiry and after observed order updates. Each call recalculates from the committed PostgreSQL snapshot. Discard expired responses and responses belonging to a replaced visit. Ready, served, collected, and fully declined orders have no remaining preparation and can be omitted from the estimate polling set.

The integrated Customer polls accepted estimates in bounded batches while tracking orders, refreshing after an observed preparation change or expiry. It requests an estimate using the same server IDs and declarations as checkout for the active cart. An unavailable estimate retries on a 15-second interval and cannot block a quote, order status, or bill read.

The Manager measures the existing recipe duration as the lower bound and sets the measured upper bound and measured per-unit option workload through `PATCH /api/v1/admin/prep-times/{id}/estimate-workload` with `upperDurationSeconds`, `expectedVersion`, and `options`. Each option includes the catalog `groupId`, `optionId`, `lowerSeconds`, and `upperSeconds`. Use explicit zero values for an option with no added work. Missing ingredients, missing calibration, or an unmeasured selected option returns `MISSING_PREP_PROFILE`. Known ingredient conflicts retain the normal ordering validation error. A running line beyond the measured upper bound returns `STALE_WORKLOAD`. An unprofiled existing order keeps its V13 station routing and never gains a retroactive estimate snapshot.
