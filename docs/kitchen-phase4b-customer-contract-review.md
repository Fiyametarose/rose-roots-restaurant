## Proposed OpenAPI edits for joint review

These are patch instructions against the checked-in draft. Apply only after the owners approve each item. Validate OpenAPI 3.1 and its examples together.

1. **Identifiers.** If v4 is ratified, tighten `components.schemas.Id.pattern` to `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Retain `format: uuid` and shared references in paths, payloads and event IDs; update examples/codecs and migrations together. Keep display numbers as strings separate from ID validation.
2. **Kitchen projection.** Amend the closed `KitchenTicket` schema with `orderReference` (1–60), `delayTargetSeconds` (1–86400), nullable UTC `preparationStartedAt/readyAt/finalizedAt`, and `itemOperations` (1–100). Each operation projects `itemId, stationId, stationName` (1–240) and nullable UTC start/ready times. Enforce exactly one entry per line server-side. Add nullable `lastRushChange` containing proposed `action, reason, actedAt, staffId` with staff-only visibility. Agree on required vs optional additions and nullability for missing historical profiles before publishing; keep nested Order unchanged unless Customer display fields are separately ratified.
3. **Kitchen reads and handoff.** Add scoped `GET /kitchen/orders/{id}` returning 200 KitchenTicket and `GET /kitchen/orders/history` returning KitchenPage, with `status` restricted to SERVED/COLLECTED/CANCELLED, existing `mode`, trimmed `q` 1–120, inclusive UTC `from`, exclusive UTC `to`, opaque `cursor` and `limit` 1–200 (default 50). Add `snapshotAsOf` to KitchenPage, and `SNAPSHOT_EXPIRED` to Problem codes only if the 409 contract and policy are agreed. Add `POST /kitchen/orders/{id}/handoff` with closed body `{status,expectedVersion}`, status constrained to existing SERVED/COLLECTED, version 1 through 9007199254740991, and 200 KitchenTicket. After coordinating migration, narrow KitchenStatusChange.status to PREPARING/READY, leaving both read enums intact. Use existing Problem responses. Assign literal history route precedence over UUID path. Preserve cancelled lines and use explicit mode-correct handoff.
4. **Allergy and pricing.** Keep `StaffReview`, `CustomerReview`, `Order` and `OrderLine` fields and enums for the first slice. Document which expectedVersion refers to item versus order. Define whether StaffReview.reason is internal, plus the exact customer-safe reviewMessage projection. Resolve substitution repricing before any such write; if a price confirmation artifact is added, bind it to proposal, current version and reviewed server amount. Preserve KES minor units, reviewed snapshot and declined-item exclusions until applicable financial policy is jointly approved.
5. **Wait and capacity.** Keep POST /wait-estimates and WaitEstimate unchanged for the first slice. Consider adding `batchCapacity` (integer 1–99) to PrepTime and PrepTimeUpdate with stored migration default 1 and explicit rollout policy for clients. For accepted orders, one candidate is an optional `remainingEstimate` on Order using the existing WaitEstimate shape; agree on its semantics, active/terminal eligibility and visibility before changing the closed schema. No extra wait endpoints or state names are needed for the first slice.
6. **Assistance.** Keep separately reviewed draft only. Candidate POST /assistance with terminal-scoped `sessionId,type,note`, UUID Idempotency-Key and 201/200 replay, GET /staff/assistance and versioned PATCH /staff/assistance/{id}. Specify the exact public return projection before enabling POST. A Customer single-resource read alone cannot restore history after restart. Propose a session-authorized paginated collection (candidate `GET /sessions/{id}/assistance`) returning safe request IDs, versions, server times and agreed statuses. Agree Customer private invalidation destination and requestVersion; use staff-only projection for staff actor IDs. Resolve BILL vs BILL_HELP, optional note normalization, acknowledgement semantics and duplicate behavior before freezing request/status enums.
7. **Realtime and security extension.** Keep /ws/v1 and existing order destinations. Amend `x-websocket` only after approving the exact CONNECT authentication header, heartbeat, receipt/ready fallback, bounded replay/deduplication, authorization failures and resynchronization protocol. Later, propose scoped Kitchen assistance and workload event branches with the common v1 envelope, IDs and safe-integer resource versions. Keep notes, prices and reasons out of payloads. Scope staff security separately from terminal bearer and Admin Manager session cookies until Admin publishes the agreed security model.
