# Shared ordering integration contract v1

**Status** Proposed draft 1 for Customer, Kitchen and Admin review. The [OpenAPI contract and JSON examples](ordering-api-v1.openapi.json) define the proposed wire shape. The paths are relative to `/api/v1`. The only deployment assumed here is one shared Spring Boot authority with PostgreSQL behind it. Customer and the staff application consume the same contract.

The ordering routes in the project specification are provisional. This draft fills gaps with device lookup, explicit closure, server quotes, allergy review and responses, and Admin device assignment. It resolves provisional Admin collection updates into resource-level PATCH operations. The fetched Kitchen and Admin branch tips both pointed to baseline `502f704` during review. No shared contract or Spring Boot endpoints were present there. The Customer Java records and service interfaces are local scaffolding. A boundary mapper will convert drafts, review metadata and wait states to the agreed wire representation after integration. The catalog and restaurant settings routes remain a separate contract dependency owned by Admin.

## Wire conventions and trust

- Wire IDs use canonical lowercase UUID v4 strings. The backend issues resource IDs. `clientLineId` is a request correlation key scoped to the draft. Database primary keys can remain internal. A table display number such as `07` and pickup references are opaque display strings. Pickup references should be unique among active Takeaway sessions at the restaurant and are never credentials.
- Timestamps are ISO 8601 date-time strings normalized to UTC with `Z`. The server clock controls expiry, event time and estimate freshness. Convert for display only.
- Money is exact integer minor units in KES, limited to the JSON safe-integer range. For example, `125000` is KSh 1,250.00. An option adjustment can be negative, while the resulting unit and extended line prices must be nonnegative. Compute line totals as quantity times the sum of the base unit price and per-unit adjustments. Subtotal sums billable line totals and total equals subtotal plus service and tax. Use checked integers or decimal arithmetic on the server. Charges default to zero when absent from configuration. Before rollout agree on charge bases, order of operations and rounding per charge. There is no implicit tip.
- All REST requests use TLS and a server-validated bearer credential. Provision each physical terminal with its own device identity and revocable credential. Session and order access is scoped to the authenticated principal, restaurant and authorized session. Kitchen can access tickets and safety information for its restaurant. Admin permission is required to change device assignment and station or preparation settings. Staff roles come from verified server credentials. Keep allergy notes out of event envelopes, URLs, diagnostics and general audit logs. Restrict access to persisted notes and preserve a separately controlled audit trail for review actions and session or assignment changes.
- Every error uses `application/problem+json` with a stable `code`, matching HTTP status and a support `traceId`. Field violations point into the JSON request using JSON Pointer. Use 400 for malformed shape, 401 for missing or invalid credentials, 403 for forbidden role actions, 404 for missing or inaccessible resources, 409 for current-state conflicts, 422 for semantic validation, 429 for rate limiting and 503 for a temporary service outage. Use RFC 9457 for the error envelope. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)

## Device and session lifecycle

The terminal resolves itself with `GET /device`. Dine-In creation uses the active authorized table mapping on the backend. Takeaway creation allocates the pickup reference on the server. The request supplies a service mode. The same terminal/mode returns its existing open session (200) or creates a new one (201). A conflicting open mode returns `SESSION_MODE_CONFLICT`. A genuine missing Dine-In mapping returns `DEVICE_UNASSIGNED`. Admin changes the mapping with version checking. Reject reassignment that would affect an open session.

The session records creation, expiry and closure. Staff initiate explicit closure subject to outstanding orders and settlement rules. Expired and closed sessions block new orders. Authorized historical lookup remains possible subject to retention policy. Returning to Welcome never closes a session. Local drafts and demo sessions stay local. They cannot grant ordering access. A pending local cart needs server catalog validation and an authorized open session before it can be quoted or sent.

## Quote, order and combined bill

1. Customer fetches catalog IDs and options, obtains the session and posts the draft to `/order-quotes`. The client sends item and option IDs, quantities, allergy data and preparation notes. The server resolves the catalog/configuration and returns the authoritative price snapshot with an expiring quote ID. Show it for review and request the wait estimate before final confirmation.
2. Customer submits the reviewed draft, quote reference and `Idempotency-Key` to `POST /orders`. Revalidate identities, session ownership and openness, item availability, quantities, allowed option combinations, price snapshot and allergy metadata. Return `PRICE_CHANGED` or `QUOTE_EXPIRED` when the accepted price would differ or the quote expired. Show a replacement quote and require customer review. Require an explicit reviewed visit declaration and require review of line-level declarations in the UI. `UNREVIEWED` on a line inherits the current reviewed visit declaration. Preserve visit and line disclosures together. A line-level `NONE` does not erase visit-level risk.
3. Scope idempotency to authenticated terminal plus session plus key. Persist the canonical request fingerprint. The first accepted request returns 201. An identical retry returns 200 with the original accepted snapshot and order ID, even if the original quote has since expired. Recover ambiguous timeouts using the same key and request. Payload changes under that key return `IDEMPOTENCY_CONFLICT`. While a matching request is being committed, return `IDEMPOTENCY_IN_PROGRESS` and retry with backoff. A changed draft or a separate order round uses a new key and quote. Clear submitted local lines only after receiving acceptance.
4. Persist the order, item snapshots, totals, initial preparation and allergy states, idempotency record and outbox entries in one transaction. Publish kitchen notifications from committed outbox records. The server returns its order ID. All accepted rounds retain the same session ID. Session order history returns current snapshots, and the combined bill uses each order's current billable amounts. Exclude declined lines, recalculate applicable charges and keep the excluded line in order history. Do not settle or refund payments from this contract.

## Preparation and allergy review

Preparation status is separate from item allergy status. An accepted order can be `RECEIVED` while one or more lines are `PENDING_ALLERGY_REVIEW`. The server computes ingredient matches, potential cross-contact and unresolved disclosures from catalog metadata and original notes. Unknown or incomplete information cannot clear a risk. The kitchen sees the original line and visit notes and the computed warnings. Only lines marked `NOT_REQUIRED` or `APPROVED_FOR_PREPARATION` are eligible to enter preparation. The server validates every transition and expected version. Takeaway finishes as `COLLECTED` and Dine-In as `SERVED`. Aggregate order state derives from line progress. All cancelled lines yield `CANCELLED`, and cancelled lines do not block the remaining eligible items from completing.

Staff can approve, request clarification, defer, decline or propose a substitution. A proposed substitution keeps the item on hold. Acceptance by the customer returns it to staff review and does not open the preparation gate. A rejection keeps it on hold for another review or decline. Any changed price needs renewed customer price acceptance before finalizing that change. A decline cancels the line and makes it non-billable. Return a customer-safe review message and current state. Keep private staff notes in the restricted audit trail. Rush and delayed state are separate from preparation and allergy review. Delay is derived from kitchen timing and rush never bypasses the review gate.

## Waiting time

`POST /wait-estimates` is a draft request scoped to an authorized open session. The server combines available qualified chefs and station capacity, queued and preparing work, menu and option preparation profiles, parallel capacity and rush priority. An available result carries minimum/maximum minutes, calculated time and valid-until time. The minimum cannot exceed the maximum and validity must end after calculation. A successful computation that cannot yield a defensible range returns `UNAVAILABLE` with a reason. Service failure returns a problem response. The customer shows the unavailable fallback on disconnect, expiry or failure until a fresh result arrives. Discard results for a superseded draft. Cart edits or a workload notification trigger invalidation and refresh. Estimates are informational and do not reserve capacity.

## WebSocket delivery and recovery

Proposed transport is STOMP 1.2 on `/ws/v1` over WSS. Authenticate CONNECT with the bearer credential in a STOMP header. Authorize subscriptions against the credential and permitted resource scope. Never put credentials in the URL. Proposed private destinations are `/user/queue/v1/kitchen-orders`, `/user/queue/v1/order-status` and `/user/queue/v1/wait-estimates`. Route customer notifications only to principals authorized for that session, and kitchen notifications only to staff serving that restaurant. Disallow client message publishing on these destinations.

`ORDER_CREATED` wakes Kitchen after commit. `ORDER_UPDATED` updates Kitchen and Customer for preparation, allergy review, decline, rush or other ticket changes. Use `WAIT_ESTIMATE_INVALIDATED` to prompt Customer to refresh the current estimate. Events carry a versioned envelope and an event ID. Order events include order ID, session ID and order version. No personal notes, allergy details or prices belong in broker messages.

Delivery is at least once. Deduplicate by event ID and ignore order versions at or below the applied version. REST remains the source of truth. On reconnect, subscribe first and buffer incoming events. Kitchen refreshes the ticket list, follows all pages bound to that snapshot and applies newer buffered updates. Customer reloads its session orders and bill. Refetch authoritative REST state on gaps or ambiguous updates. A Kitchen update can be resolved by reloading the ticket list, including when a ticket leaves the active queue.

## Contract ownership and implementation

| API or event | Spring Boot implementation lead | Consumers and collaborators |
| --- | --- | --- |
| `GET /device`, terminal provisioning and credential lifecycle | Admin (member 3), shared security | Customer reads device, staff provisions devices |
| `PATCH /admin/devices/{id}/assignment` | Admin (member 3) | Admin updates, Customer displays resolved table |
| `POST /sessions`, `GET /sessions/{id}`, `POST /sessions/{id}/close` | Customer (member 1) | Customer starts/resumes, authorized staff closes |
| `POST /order-quotes`, `POST /orders`, `GET /orders/{id}`, `GET /sessions/{id}/orders`, `GET /sessions/{id}/bill` | Customer (member 1) | Customer reviews and tracks, Kitchen consumes persisted snapshots, Admin provides price configuration |
| `POST /orders/{id}/items/{itemId}/review-response` | Customer (member 1) | Customer replies, Kitchen defines review guards with member 1 |
| `GET /kitchen/orders`, `PATCH /kitchen/items/{id}/status`, `POST /kitchen/items/{id}/allergy-review`, `POST /kitchen/orders/{id}/rush` | Kitchen (member 2) | Kitchen ticket workflow, Customer reads outcomes |
| `POST /wait-estimates`, `WAIT_ESTIMATE_INVALIDATED` | Kitchen (member 2) | Customer requests and displays, Admin configures profiles |
| `GET /admin/stations`, `PATCH /admin/stations/{id}`, `GET /admin/prep-times`, `PATCH /admin/prep-times/{id}` | Admin (member 3) | Admin configures, Kitchen computes capacity |
| Catalog item IDs, option IDs, allergen data and settings (separate catalog contract) | Admin (member 3) | Customer browses and quotes, Kitchen reviews and estimates |
| `ORDER_CREATED`, `ORDER_UPDATED`, secure broker and reconnect | Kitchen (member 2) owns transport, Customer (member 1) owns order outbox writes | Kitchen consumes both, Customer consumes updates and resynchronizes |

## Decisions before adoption

- Confirm public UUIDs versus the specification's suggested Long IDs and agree on catalog ID and allergen-code mapping, including legacy `NUTS_UNSPECIFIED`.
- Agree on token issuer and provisioning, staff permissions, token rotation, common contract ownership and the point at which versioned DTOs move into the shared module.
- Agree on session and quote lifetimes, idempotency retention, permitted concurrent sessions, closure and recovery policy and privacy retention.
- Finalize tax and service-charge bases and rounding, customer repricing approval for substitutions, and later settlement/reconciliation for declines after payment. Payment itself is outside this draft.
- Confirm waiting-time capacity and priority rules, destinations and delivery rollout, ticket snapshot cursor behavior and customer-safe review reason wording.

Validate the OpenAPI document as 3.1 and validate every embedded request, response and event example against the referenced JSON Schema 2020-12 schema. Status transitions, authorization, arithmetic, concurrent idempotency and post-commit delivery require integration tests when the backend is implemented.
