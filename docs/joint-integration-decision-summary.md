## Shared database and security work

Admin should reserve the next unused version after synchronizing branches, test upgrades from deployed V5 as well as fresh schemas, and leave applied migrations intact. - Proposed migration scope covers terminal identity and table assignment, server sessions, quote snapshots, accepted order and line snapshots, canonical idempotency fingerprint and saved accepted response, and a durable outbox. Keep foreign keys and scoped uniqueness, particularly terminal/session/key. Preserve prices, options, notes, allergy and timestamps server-side and keep private data out of events. - Place validation, order/line snapshots, billable totals, idempotency and outbox in one transaction. Kitchen writes compare the expected line version, serialize aggregate order status and increment affected versions atomically with their outbox row. Retry delivery after commit and verify that rollback emits no event. Reconcile concurrent bill/history reads by authoritative refresh before replacing the visible snapshot.
- Admin should add and test terminal provisioning, bearer validation, session ownership and staff restaurant/action scope alongside its existing Manager form-login/CSRF chain. Verify unauthorized cross-session, cross-restaurant and stale-version cases. No role or trusted table supplied by a desktop client.
- Confirm receipt behavior on the actual configured broker by observing a SUBSCRIBE receipt before REST sync. If unsupported, jointly specify a ready signal and test reconnect without a missed-update window. Admin's actual LAN guide uses database host port 5434 by default and `ROSE_BACKEND_URL`; Customer currently reads `ROSE_ROOTS_BACKEND_URL`. Resolve naming after approval, retain TLS validation, and probe the configured DB host port as well as HTTPS from PC 1.

## First executable plan after approval

1. **Admin** starts one shared backend and its PostgreSQL, applies the approved migrations to an isolated test schema, provisions one authorized table terminal and one staff principal, and makes one catalog dish with verified safety and pricing available. Confirm HTTPS certificate trust on both Windows PCs. PC 2 runs the shared Staff app and server; PC 1 runs Customer independently.
2. **Customer** opens the authorized Dine-In session, reviews the server quote and submits one item through HTTPS. Record server order/line/session IDs. Retry with the identical key and request and verify the same ID and exactly one durable order. Reject changed input under the same key.
3. **Kitchen** reads the ticket through HTTPS under staff scope and moves the matching line to PREPARING and then READY using current versions. Verify each persisted state from Customer's authorized GET and that READY remains active with no automatic finalization. Check that stale writes and preparation of an uncleared allergy line are refused.
4. **All owners** run the physical LAN acceptance after the agreed broker setup. Establish real WSS subscriptions; observe an order transition arriving from PC 2 without manual refresh. Disconnect PC 1 for a transition, reconnect, and verify subscription readiness followed by REST order/bill resync to the same persisted IDs and latest state. Verify a later WSS update and that the PC 2 database port is inaccessible from PC 1. Capture matching IDs, versions, timestamps and evidence on both PCs. A localhost or fixture-only run cannot establish this result.
5. After that one-order proof, submit a second independently keyed round to the same session and verify one combined bill. Exercise declined-line exclusion and explicit mode-specific handoff once their approved operations are available.
