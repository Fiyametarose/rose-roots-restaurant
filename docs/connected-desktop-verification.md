# Connected Customer and Kitchen/Admin walkthrough

Use Java 21 and the same integration revision for both distributions. Run `./gradlew.bat clean build :installDist :kitchen-app:installDist` with the `ROSE_TEST_DB_*` settings pointed at disposable PostgreSQL to include the database tests. Use the catalog and LAN profiles for the running backend, a certificate trusted by both client JDKs, and the same HTTPS origin in both client environments. Use a provisioned table terminal, an individually issued Chef bearer with allergy-review permission, and the separate Manager sign-in. Keep tokens and passwords out of evidence. See [database setup](database-environment.md), [terminal provisioning](ordering-backend-4c2a.md), and [Chef provisioning](ordering-draft-2-handoff.md#chef-credential-provisioning).

1. Launch the Customer distribution with `--connected`, `ROSE_ROOTS_BACKEND_URL`, and `ROSE_ROOTS_TERMINAL_TOKEN_FILE`. Launch Kitchen/Admin with `ROSE_KITCHEN_MODE=connected`, `ROSE_BACKEND_URL`, and `ROSE_KITCHEN_STAFF_TOKEN` in a separate shell. Set the URL to the trusted origin without an API path. Confirm Customer displays the provisioned table and Kitchen shows Server connected.
2. Add a dish with priced options, edit the cart line and quantity, and confirm the automatic restaurant quote. Verify known ingredient and known selected-option allergy conflicts block the affected configurations. Submit a valid order without allergies and record its order ID. Confirm automatic Kitchen discovery and Customer readback of PREPARING and READY. Confirm the order remains in Handoff until staff explicitly marks it Served.
3. Start another round in the same visit. Confirm the cart is empty before adding new lines. Submit one ordinary line and two lines that disclose an allergy without a known ingredient conflict. Advance the ordinary line while the others are held. Approve one held item and decline the other with a reason. Confirm the approved item can advance, the declined item remains visible in history, and the payable bill includes both rounds minus the declined amount.
4. Submit every Assistance request type offered by Customer. Confirm automatic Kitchen discovery and match request IDs. Follow one request from Submitted through Acknowledged, In progress, and Completed, checking Customer after each action.
5. Before any item is served or collected, verify review submission is unavailable in a fresh visit even when food is READY. After handoff, open Customer Orders and send a 1-star food review with a distinctive comment. Verify Customer acknowledgment, persistence after reopening Orders, and duplicate prevention. Confirm the same feedback appears in connected Kitchen Reviews and in Manager analytics. Sign in to Admin separately, save a follow-up, reopen it, and confirm that Kitchen cannot read the private follow-up. On a new eligible visit, skip the review and confirm no review or rating is created.
6. Start or switch to a different authorized visit. Confirm orders, bill, Assistance, review drafts, and review acknowledgment from the prior visit do not appear there. Record revision, scenario, timestamps, and IDs where available. Keep desktop and PostgreSQL evidence distinct from REST fixture evidence.

## Staff operations

1. In Manager **Staff & Security**, create a Chef and a Kitchen Supervisor. Grant allergy review only to the qualified Chef. Supply each distinct issued credential through its staff launcher environment. Admin Managers use their own sign-in password.
2. In Manager **Kitchen Configuration**, assign the Chef to a station, set that station's parallel slots, and set the Chef's availability. Confirm the server reports one assigned and available Chef. Save a preparation profile for a catalog item and submit another round containing that item. Verify the line appears in the selected Kitchen station. Existing orders retain their original routing.
3. Mark and remove both Rush and Delayed from the connected Supervisor Priority Queue and from the Manager's Order priority tab. Enter a reason for each change. Verify an ordinary Chef cannot make these changes and a Rush order still cannot start a held item.
4. Open **History & Sync** after explicit service or pickup. Find the same order UUID, final state, and recorded handoff time. Check that disabled managed staff credentials and Manager sessions lose access on their next server request.
